结论

  • 用户实际等待 7.86s → 3.52s（2.23×）。其中最大一笔不是"转换"，而是两处与转换无关的等待：进度线程的 200 ms 轮询 join，以及临时目录清理。
  • 解压提升 2.16×（2.12s → 0.98s）。实测瓶颈不是 Deflate 解压（15 MB，约 0.05s），而是 3 631 次逐文件创建 + 杀软扫描；作为对照，PowerShell 的 Expand-Archive 处理同一个包需要 6.7–7.4s。
  • 引擎开销降低 67%（1.40s → 0.46s）。38 个任务本身仍是 1.48s —— 提速没有通过"少做事"获得。
  • 提速完全无损。优化前后产物在严格模式下字节级一致；这一点由自动化闸门保证，后续任何提速改动都必须通过它。
  • 剩余空间：打包 0.55s（可并行化）与任务长尾（38 个任务中 31 个 < 0.05s，多为重复扫描目录，可用"文件索引一次遍历"消除）。

方法学

  • 输入：TapL 16x.zip — 3 631 个文件 / 18.41 MB / 4 018 个条目，pack_format 1（1.6–1.8）→ 97（26.3），输出 [Java 26.3] 同尺寸级。
  • 环境：同一台 Windows 机器、24 逻辑核、同一 debug 构建；每个时间点连跑 2–3 次取稳定值，剔除首次冷启动。
  • 计时口径：pure = 引擎（预检 + 管线 + 收尾，不含文件 IO）；total = 含解压与打包；cleanup = 临时目录清理（后期改为异步，故不再计入 total）。
  • 关于"隐性开销"：清理发生在计时快照之后，早期版本中它既不在 pure 也不在 total，只在批处理墙钟里出现（一次 GUI 运行的 6.02s 中占 2.27s）。图中以斜纹段标注，这是"用户等待 vs 进程内测量"两种口径差异的来源。
  • 外部秒表的干扰：用外壳（PowerShell & / Start-Process -Wait）测得的墙钟可能额外包含控制台输出渲染与删除子进程的存活期；程序内部实测为 3.74s（结构分析 0.21s + 转换 3.52s），两者差异属测量方式，而非程序在等待。
  • 数据来源：各节点的日志行 conversion timing: / engine breakdown: 与同日提交记录（63bf845 进度线程与并行解压、7db083c 清理计时与异步、6662465 脱离进程清理与日志 flush）。
  • 更新数据：本页是单文件、零依赖的静态页面。新增时间点时，编辑 <script> 顶部的 MILESTONES 数组即可（每项含 extract/engine/pack/cleanup 四个耗时与说明），图表、表格与加速比会自动重算。数值可由 2-pyramid.exe --convert <包> --to <版本> --report 报告.json 直接取得。
内部基准：单机、单输入包、debug 构建，用于工程决策，不代表所有包或发布版的表现；结果可能随输入规模、磁盘与杀软设置变化。 由 2-Pyramid 的 --convert（结构化 JSON 报告）与 --pack-diff（质量闸门）自动产出数据。

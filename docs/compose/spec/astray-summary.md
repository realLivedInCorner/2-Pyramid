> **状态：已完成（M0–M3 全部收口）。** 46 个转换任务全部原生实现，旧引擎（`hurray/`）与旧转换器树（`converters/`）已删除，生产二进制不含旧转换器代码。

> **落点**：任务实现在 `src-tauri/src/natives/`，元数据在 `src-tauri/src/task_registry.rs`，引擎在 `src-tauri/src/arom/`。冻结内容基线 **4018 条目 / 指纹 `0x75bb3260e7f578a6`** 全程未变；debug 纯转换 6.01s → 3.55s（详见 `perf-verification.md`）。

## 1. 变更定性（治理前提）

### 1.1 破坏性变更的确切含义

| 维度 | 结论 |
|---|---|
| 破坏等级 | 内部设计级：转换器签名与任务体、`HurrayContext` 契约、「临时目录是唯一真源」这一假设、贴图缓存键、任务间通信、解压/打包主路径、调度与并行模型 |
| 对外目标 | 零变化：用户可见行为与产物 zip 字节不变 |
| 允许的对外破坏 | 仅限显式列出并裁决过的条目（当前：无） |

### 1.2 解除 Foray 阶段的锁定条款

2.5.0 的 Foray 设计明确锁定过四条与本变更冲突的条款，Astray 是它们的「未来迁移特性」，现予解除：

| 原文 | Astray 的处理 |
|---|---|
| 「ROM：Foray 侧独立 ROM，不改写 Hurray 104 个转换器；Hurray 继续文件流」 | 解除：A-ROM 成为唯一内核 |
| 「**禁止**在本特性内把转换器改成对象操作」 | 解除：本变更的全部内容就是这个 |
| 「未来 Master Enzyme 实时编辑走 ROM 时，另开迁移特性（Out of Scope）」 | 认领：Astray 即该迁移特性 |
| Out of Scope：「改写 Hurray 104 个转换器 / 全量测试重写」 | 移入 In Scope（分期见 §7） |

**边界**：只解除转换器与文件操作模块的**执行形态**；产品语义、用户可见行为、以及 Foray 已立的安全边界（Zip Slip / Bomb / 符号链接 / 深度 / 体积上限）继续有效。

### 1.3 交付判据

- **G1 单一模型**：一次转换全程只有一个受管对象模型；临时目录最多是溢出后端。
- **G2 类型化契约**：转换器不再接收 `temp_dir` / `&Path`；任务间不再用字符串字典传隐含语义。
- **G3 保真可证**：未触碰条目字节保留；产物与迁移前**逐项一致**（内容 / 条目集合 / 压缩方法 / 权限位；时间戳与顺序除外，见 §5.1）。
- **G4 可观测**：每个条目的来源、被哪个任务改过、改成什么，由层结构直接给出。
- **G5 单一内核**：Foray 与引擎共用同一模型，不再维护第二棵树。

## 2. 现状与证据

### 2.1 一次转换的物理形态：中间产物自始至终是磁盘路径

```
输入 zip
  → 建临时目录 .2pyr-work-*
  → 解压落盘（并行写盘）
  → 预检全部读盘（含结构分析）
  → 建上下文（只持有路径 + 两个字符串）
  → 注册 88 个任务闭包
  → 分层执行，任务各自 join 路径读写临时树
  → 延迟清理清单一次性执行
  → 重新打包（未排序的目录遍历）
```

矛盾集中在两个结构体：

```rust
// hurray/context.rs:62
pub struct HurrayContext {
    temp_dir: PathBuf,
    shared_data: RwLock<HashMap<String, String>>,            // 任务间唯一通信渠道，字符串键值
    texture_cache: RwLock<HashMap<PathBuf, Arc<RgbaImage>>>, // 缓存键是磁盘路径
    cleanup: RwLock<CleanupList>,                            // 删除靠延迟清单，顺序敏感
}

// hurray/scheduler.rs:28 —— 没有 converter trait，是裸闭包
type TaskFn = Arc<dyn Fn(&HurrayContext) -> Result<(), String> + Send + Sync>;
```

转换器三种输入形态，全部直接从磁盘取数：`&HurrayContext` 48 处（内部只取 `temp_dir()`）、`: &Path` 参数 192 处（含测试代码）、少数纯像素函数。

### 2.3 为什么「再加一层」解决不了

1. **语义无处表达**：任务间只能传 `String → String`；「某文件被谁改过、改成什么、是否应原样保留」没有类型化表示。
2. **磁盘是唯一真源**：每个任务自己拼路径读写；贴图是否已解码要靠人工判断缓存；同一张图可能反复解码。
3. **正确性依赖顺序自觉**：删除是延迟清单，新任务必须记得登记清理；转换链**完全没有**备份/原子替换（全仓只有 Foray 导出侧有）。
4. **可验证性只在端到端**：唯一强闸门是 `--pack-diff`，而它本身有证明力缺口（§5）。
5. **样板重复 154 次**：拼路径 → 读 → 改 → 写 → 登记清理 → 想缓存失效。
6. **两棵树 + 两套 mcmeta**：Foray 侧 ROM 与 Hurray 文件流零复用；mcmeta 有两套独立实现；结构知识散在第三处（只读分析模块）。
7. **死代码占位**：54 个旧注册函数与从未实例化的引擎包装。

## 3. 为什么不能照搬 Foray 的 ROM

Foray 的 ROM 是为「单包 · 单线程 · 读多写少 · UI 展示」设计的，与引擎需求正面冲突：

| 冲突 | 具体表现 |
|---|---|
| **生命周期错** | 读完即关闭容器句柄，导出时必须重新打开源包逐条复制——这个「对象模型」无法独立成立，始终挂着磁盘 |
| **内存形态错** | 每个条目全量常驻字节且**急切计算 SHA-256**，容器表无索引；1 GiB 包不可能，且为用不到的哈希付费 |
| **真源形态错** | 嵌套目录树 + 节点重复存路径字符串 + 查找是全树递归 O(n)；92 个任务各查几次就是平方级 |
| **结构表达错** | overlays 只有一个布尔值；空目录条目直接丢弃；不携带 unix 权限位——转换链要保真的东西恰好都表示不了 |
| **变更模型错** | 单个 dirty 标记 + 导出时比对，无层、无事务、无来源追溯 |
| **消费假设错** | 连序列化派生都没有，前端拿的是临时投影 |
| **质量信号** | 分类函数里有一个两支返回相同的冗余分支，说明它从未被当引擎内核压过 |

**只借鉴三样东西**：① 安全解压的**校验规则**（Zip Slip / 重复路径 / Bomb / 深度 / 体积上限）——安全知识而非数据结构；② 原子替换范式（备份 + 临时文件 + 替换/回滚）；③ 「未改动条目原样保留」的纪律。

**Foray 的归宿**：其 `Rom` / `RomFile` / `RomDir` 类型**退役**，Foray 改为 A-ROM 的消费者，前端 JSON 契约不变。

## 4. A-ROM 设计

### 4.1 设计驱动（来自引擎负载，不是来自 UI）

92 个任务的三级分层与并行/独占混合 · 上限 50k 条目 / 1 GiB（现实样本 3.6k 文件 / 18 MB） · 同输入必须同字节（否则闸门无意义） · 未触碰条目字节保留 · 双消费者 + CLI（引擎并发写重、Foray 单线程读多、CLI 只读） · 多根 / overlays / 版本折叠目录 / Java↔Bedrock 整树重排 · **目录级改名是常态**（逐条目物化会爆） · 包外资源（UImage 模板） · 逐任务计时与报告。

### 4.2 分层

```
L4 Facade     引擎（&PackView + Tx）  ·  Foray 编辑投影  ·  CLI 只读
L3 Structure  多根 · overlays 分层 · 版本折叠目录 · pack_format(min/max) · 目标版本维度
L2 Views      按需类型化视图：mcmeta() · image(path) · model() · lang() · manifest()
L1 Store      arena<EntryId> + 路径驻留 + path→id 索引 + ContentRef + Layer/Tx
L0 Sources    ZipSource（句柄常开，可取原始压缩字节） · BlobSource（内存/溢出） · DirSource
```

### 4.3 四个关键机制

**① L1 变更表示：CoW 层 + 路径覆盖映射**

源包 = 不可变 base 层；每个任务/阶段写自己的层；`commit` 按层序合并，`abort` 丢弃整层。

- **未写入的路径自然字节透传** —— 保真从「不写就不变」的惯例变成结构；`dirty` 标记不再需要。
- **回滚与并行隔离变成结构性的**：回滚 = 丢层。
- **「谁改了什么」由层直接给出**，可观测性不需要额外埋点。
- **目录级改名用前缀重写规则**（解析时惰性生效），不物化 3k 个条目。
- 冲突检测：同一路径被两个并行层写入 → 合并时报冲突（建议默认拒绝，可配「后者胜 + 告警」）。

**② L0 来源：句柄常开 + 惰性字节 + 顺序契约**

持有容器句柄直到包生命周期结束（解决「导出要重开源包」）；条目元数据常驻、字节按需读取；**索引顺序 == 容器内顺序**，这是产物确定性的前提。句柄池支撑并发读——实测 1000 条目全量读 **9.33 ms**，而每次重开容器需 **2.49 s（约 267×）**。哈希按需计算，不再是构建期成本。

**③ L2 视图：按需类型化 + 缓存失效**

存储只管条目与字节；`mcmeta()` / `image(path)` / `model()` 等类型化视图按需解析、缓存、写入即失效；未识别类型退化为原始字节视图，**不付解析成本**。两套 mcmeta 实现在此收编为一套。

**④ 任务契约：声明读写范围**

任务声明「读哪些路径、写哪些路径」，引擎据此建冲突图：**写集不相交才并行**，独占任务作为屏障；调试模式下写入未声明路径即报错。这取代了今天「靠分层表 + 注册顺序」的隐式约定。调度骨架（三级分层、拓扑、进度、计时）保留不动。

### 4.4 并发、确定性与内存

- 视图不可变共享，写只经事务句柄 → 不需要用锁包住整个模型（现状是四把锁）。
- **确定性契约**：条目迭代顺序 = 源顺序；层合并顺序 = 阶段与任务注册顺序；blob 命名与溢出位置不得影响产物字节。
- **内存策略**：源包句柄常开按需读取，变更驻内存、超预算溢出到受管后端，输出流式写。建议默认预算 512 MiB / 包（可配），大条目（>8 MiB 或不可解析类型）默认不进内存；预算并入现有「性能档位 / 线程预算」体系。基准包为真实样本与逼近 1 GiB 的合成包。

### 4.5 源包只读与写回

源包全程只读；输出走「临时文件 + 原子替换 + 失败回滚」；Foray 的「原地覆盖」与转换的「另存」共用同一条序列化路径。

## 5. 保真与验证策略（本次最关键的发现集中在这里）

### 5.1 现状输出契约（字节对齐的基线，逐条实测）

| # | 契约 | 说明 |
|---|---|---|
| 1 | 条目集合 = 文件 ∪ **磁盘上的目录条目**（空目录会保留） | 有测试断言空目录存活 |
| 2 | 文件内容 = 磁盘字节；未触碰者 = 源字节 | PNG 等走 `Stored`，未改写即原样进包 |
| 3 | 压缩方法 = 扩展名白名单（`.png/.ogg/.jpg/...` → `Stored`，其余 `Deflated`） | 确定 |
| 4 | 时间戳 = **运行时刻**（`FileOptions::default()` 取 `OffsetDateTime::now_utc()`，DOS 精度 2 秒；**不是源时间**） | 因此**不可跨运行比较**——实测真实包 3723 条目里 428 条落在不同 2 秒桶 |
| 5 | **unix 权限位不保留**：只在 unix 构建下用于拒绝符号链接，Windows 整段编译掉 | 全仓无设置权限的调用 |
| 6 | 条目顺序 = **未排序**的目录遍历顺序（无契约保证） | 因此「容器逐字节一致」必须先定义顺序 |

由此两条纪律：**「模型保留信息」≠「输出策略」**（模型要能携带权限位/时间戳/原始压缩字节，但转换输出策略必须与现状一致，否则红线当场变红；Foray 导出路径可另选策略）；**顺序与时间戳都不是现状承诺**（两者都作信息项，不判失败）。

### 5.2 闸门升级（Step 0，已完成；时间戳语义在 M1 修正）

旧闸门把容器读成「路径 → 字节」，因此**看不见**三件事：目录条目、压缩方法、zip 元数据。新增容器级比对：

| 差异类型 | 判级 |
|---|---|
| 目录条目单边存在（空目录丢失） | **两种模式都失败**（旧闸门静默忽略） |
| 压缩方法不同 | 仅严格模式失败 |
| 内容相同但压缩字节不同 | 仅严格模式失败 |
| unix 权限位不同 | 仅严格模式失败 |
| **时间戳不同** | **只报告不判失败**（M1 修正：两边都盖运行时刻，跨运行必然不同；此前能过是运气） |
| 条目顺序不同 | **信息项**，不判失败（但严格通过时的措辞会明说「不构成逐字节一致」） |

报告 JSON 为纯加法，既有字段与退出码语义不变。验收：三种人为扰动（空目录 / 权限位 / 压缩方法）必报红，7 个用例覆盖（含「仅时间戳不同必须通过严格模式」）。

### 5.3 闸门上线立刻抓出的设计错误（重要）

设计文档原写「未触碰条目 = 原始压缩字节透传 → 不重压缩」。**这对 `Deflated` 条目是错的**：

| 情形 | 现状产出 | 原样透传产出 | 结果 |
|---|---|---|---|
| 源 `Stored` + 白名单 `Stored`（PNG/OGG） | 源字节 | 相同 | ✅ |
| 源 `Deflated` + 白名单 `Stored`（被压过的 PNG） | 解压后 `Stored` | 仍为 `Deflated` | ❌ 方法不同 |
| 源 `Deflated` + 白名单 `Deflated`（JSON/mcmeta） | 解压后按本仓默认级别重压 | 源压缩字节（级别可能不同） | ❌ 压缩字节不同 |

**修正后的策略**：只在「源方法 == 白名单方法 == `Stored`」时透传，其余解压后按现状设置重压。收益仍然真实——占体积大头的 PNG/OGG 永不 inflate，且全程没有临时目录与磁盘往返。

**这条教训本身就是「先做闸门再动内核」的理由**：这句错话若留到序列化步骤才暴露，代价是重写序列化器。

## 9. 风险与未确认

**风险**

1. **内存策略**（最大技术风险）：现有设计以磁盘为真源，惰性后端需明确预算、溢出与并发句柄管理；建议在 Step 4 前做一次基准（真实样本 + 逼近 1 GiB 合成包）。
2. **顺序契约**：现状顺序不确定，A-ROM 必须自己定义确定顺序（D20），否则「逐字节一致」无法判定。
3. **Foray 迁移**：其模块要从「自有树」改成消费者；前端契约不变，但回归面集中在导出与探针。
4. **过渡期双视图**：兼容适配层允许未迁移任务继续用路径形态，代价是两套视图并存——必须限定在迁移期并在收口时删除。

**未确认（不当作事实）**

- 无调用点的若干模块（遗留处理器、若干贴图/音频模块）是否为将来版本预留。
- GUI 前端实际调用三个转换入口中的哪一个。
- ~~`docs/` 被整目录忽略是有意还是遗漏。~~ → **已在 M4 收口时定清**：有意为之，但收窄为"大部分不入库 + 3 份例外"，见上方「D8 的落地结果」。
- 无头模式的 `--setting` / `--exit` 是否有外部使用者。
